# 蓝牙启动连续内存与音频并行诊断

安卓0.4.0安装后，用户在设备“蓝牙遥控”入口遇到“内存不足”。读取s3.48现场状态时，设备只运行桌面及设置，所有播放器、在线助手和离线识别均不活动；内部空闲70027字节，其中DMA空闲62335字节，但最大连续DMA块只有29696字节。停止操作后再次读取，最大块仍为29696字节。

ESP32-S3控制器启动需要0x7800（30720）字节连续内部块。现有启动保护同时要求DMA总余量至少40KiB，因此这次被连续块条件拒绝。PSRAM仍余约2.4MiB；歌曲和故事文件继续保存在SD卡，减少媒体文件数量不能合并内部空闲块。

## s3.49分配策略

保持普通malloc优先使用PSRAM（`CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=0`）和NimBLE主机外部内存配置；将`CONFIG_SPIRAM_MALLOC_RESERVE_INTERNAL`从32768提高到65536，调整启动时内部DMA/显式内部内存池的布局和分配优先级。总物理RAM不变，也没有新增媒体缓存。控制器的30720字节连续块及40KiB总量检查保留。

此配置由固定ESP-IDF 6.0.2的`esp_psram_extram_reserve_dma_pool()`实现，池会根据实际堆区域分配，可能包含多段。因此验证以实际最大块、启动结果和连续使用后的重复测试为依据。

## 诊断字段

USB本地`PhoneProvisioning.GetState`新增：

| 字段 | 含义 |
| --- | --- |
| `start_attempts` | 进入蓝牙启动流程的次数 |
| `memory_rejections` | 启动前内存保护拒绝次数 |
| `start_largest_dma_block` | 最近一次启动前的最大连续DMA块 |
| `start_dma_free_bytes` | 最近一次启动前的DMA总余量 |
| `required_dma_block` | 控制器所需连续块，30720字节 |

判断启动条件使用`start_`字段；`active`时的剩余块已经扣除控制器分配。配对码不进入这些诊断记录。

## 复测

`phone-remote/tests/verify_ble_memory_reuse.py`依次检查初始启动、多轮十应用打开/关闭、播放及十秒诊断睡眠淡出后再次启动/关闭蓝牙。测试核对真实广播开启、启动前连续块和总余量、拒绝计数；保留音量、深睡选项、书签、两类播放模式和50个音频文件。

```powershell
python phone-remote/tests/verify_ble_memory_reuse.py --port COM5 --rounds 3
```

s3.49完成三轮十应用打开/关闭及三次诊断淡出，7次蓝牙启动/关闭全部通过；启动前最大连续DMA块为53248～57344字节（52～56KiB），DMA总余量最低59307字节，内存拒绝计数未增加。30篇故事、20首儿歌、14个应用及原音量/书签保留。

随后用`verify_songs_device.py`进行真实加密BLE连接及儿歌播放/硬件音量/定时检查。该测试使用安卓APK相同的Java安全协议实现，电脑需要开启蓝牙。

原始状态、循环测试和完整运行日志只留在忽略的runtime目录。安卓0.4.0继续使用原签名安装包，本次修复更新设备应用分区，保留NVS、LittleFS、SD应用和音频。

### s3.49真实连接结果

在上述暖机循环之后，安卓同源Java Security1协议与实机建立连接，五轮读取完整20首曲库，播放/切曲/暂停继续、三模式、15/30/45分钟及取消、codec/DAC实际调音均通过；20秒蓝牙轮询播放零断粮，最大输出间隔12.334ms。30故事、20儿歌、14应用保留，原音量62%、模式及书签恢复，电脑蓝牙恢复原状态。

早期一次目录断言失败未记录返回内容，工具补充了末次请求和响应；随后五轮目录及完整控制通过。SDK既有的共享电源依赖日志可能混入USB串口，测试客户端只在明确的audio_dac占用AXP及短时间匹配的日志链内分离诊断，其他错误仍失败；5项回归检查覆盖真实DMA错误、无先导/过期日志与无效JSON不能被忽略。原日志和测试失败记录只留在私有runtime目录。

有限轮次结果用于确认本次复现已覆盖；运行中的最大块、成功启动前的最大块和内存拒绝数分别记录，便于持续排查。用户已现场确认安卓0.4.0连接成功、儿歌页正常。

### 2026-11-05 助手并行诊断（s3.51）

用户反馈手机蓝牙连接后，小马助手提示未找到麦克风或喇叭。普通状态及真实加密BLE下，两种助手各两次本地录音回放均成功（每次48000采样帧，输出90240～96000字节），小智单独连接进入Ready；尚未复现原硬件提示。

重复音频测试后蓝牙暖启动保护拒绝：DMA总余量61311字节，但最大连续块23552，小于30720字节要求。这是另一个已复现的内部内存碎片问题，不能直接视为原提示根因。后续应覆盖前台JS助手、TLS及手机真实操作路径，不能只用原生音频自检代替。

尝试把16/8KiB助手控制栈放PSRAM后，本地录音通过，但连接持久化路径触发`esp_task_stack_is_sane_cache_disabled()`保护断言；该候选已撤回，恢复s3.51内部控制栈，不发布候选安装包。安全后续方向包括保留内部Flash/NVS调用栈，按实测栈峰值调整尺寸，或把持久化操作交给内部栈工作任务，必须完成TLS与存储路径实机验证。

`verify_assistant_audio_device.py`用于进一步复现：真实BLE鉴权、两类本地录音回放、前台助手重复连接及暖启动；失败时不应标记整体通过。原始日志仅在私有runtime，录音未上传。仍需用户手机现场复现原报错。

### s3.53 麦克风读取恢复

手机现场复现的具体提示为“麦克风读取失败”：首次读取尚未得到任何帧，上传包数0；控制栈余量12696/16384字节，编解码栈只使用1036/49152字节，未触发40KiB栈保护。随后同一手机连接下本地录音回放成功48000帧，说明不能将该次失败等同于硬件缺失或栈溢出。

小智捕获函数最多尝试3次读取，失败后仅重开自身Recorder，两次重开间各等待20ms，取消后停止重试，仍失败时停止并报错。不会重建共享HAL/I2S提供者，不释放其他音频服务接口；新增`capture_read_retries`诊断。保留内部控制任务栈及原保护。此恢复用于处理瞬时RX故障，底层失败原因仍需后续日志；不声称消除了另一个暖启动碎片问题。

### s3.54 启动阶段共享驱动寿命

s3.53自检在启动后复现“未找到麦克风或喇叭”。冷启动日志显示：初始音量探测临时获取Audio接口，最后句柄释放后注销CodecPlayer/Recorder并释放RX；TX仍被板级DAC持有，随后重新初始化RX出现`i2s controller 0 has been occupied`。这与原先仅在OfflineVoice启动后保留Recorder的策略存在时间空窗一致。

s3.54在`start_audio_services()`入口、DeviceModes/AudioPlayback/OfflineVoice绑定之前，静态持有两类HAL接口，贯穿系统运行，避免引用计数归零导致驱动提供者被反复销毁。仅保持接口寿命，录音/播放仍按会话开关；不绕过家长策略，也不后台采集音频。保留有限读取恢复与内部控制栈。

s3.54验证进展：应用分区读回校验通过；两次重启均记录recorder=1/player=1，启动日志不再出现RX释放、Audio接口注销或I2S占用。真实加密BLE下LocalVoice及VoiceAssistant各一次三秒本地录音/96000字节回放通过。完整循环测试中途未完成，未记为全通过；手动清理电脑BLE并恢复关闭后，设备遥控入口重新开启成功，正在等用户手机真实对话确认。

用户随后在手机连接场景连续两次确认“说话→发送”正常识别和播报。设备状态记录captured_frames=165120、sent_packets=171、received_packets=194、played_bytes=362880、capture_read_retries=0，证实本轮实录/上传/回答输出链路正常。遥控入口重开时最大DMA块38912字节，memory_rejections=0；有限轮次不能替代长期压力测试。

仍有独立待办：本轮一次SPI显示`Failed to allocate priv TX buffer`，当时助手仍运行，内部余量约10411、最大块4096字节。已保留私有原始日志，后续需要针对显示DMA缓冲/内部余量继续优化，不把本次生命周期修复表述为解决全部内存压力。

### s3.55：助手使用后的蓝牙连续内存不足

内部DMA/内部专用预留池由64KiB扩大到96KiB，保持普通分配优先PSRAM、64KiB音频PCM缓冲、共享双工Codec寿命及内部控制任务栈。扩大的是启动时隔离出来的内部池，不是增加物理RAM；一般堆分配仍使用PSRAM，驱动/必须内部的任务可使用保留区域。不能因此承诺任意负载下永不碎片化。

`verify_ble_memory_reuse.py`增加两类助手完整三秒录音回放及小智TLS连接/关闭，然后再启动蓝牙；覆盖应用/音频/睡眠后的重复启动。测试保留音量、播放模式、书签与深睡选项。

### s3.56：限制显示刷新临时DMA峰值

s3.55五次重开通过，但真实加密BLE并行测试在第二轮前台助手连接时仍抓到SPI私有TX缓冲分配失败；四次录音回放和第一轮前台Ready已通过，整轮失败未标为通过。不能据五次启动就声称并行问题解决。

S3使用PSRAM全屏绘制缓冲，SPI驱动可能为每个在途分块申请内部DMA中转；默认两笔队列、9600请求经IDF取整到12276字节，瞬时峰值可超过24KiB。s3.56固定队列深度1、请求最大传输3840（板级生成器取整为4092字节），将这部分峰值约束到一笔约4KiB。保留PSRAM全屏绘制及全帧完成回调，图标/九宫格尺寸不变；不绕过DMA错误，也不在失败时复用尚未结束的缓冲。配套第十二份上游补丁重建板级配置。
